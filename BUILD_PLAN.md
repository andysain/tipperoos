# Tipperoos EPL Rebuild — Build Plan

Produced via a 4-agent fan-out / cross-examine / adjudicate process (Ship-it, Data model & scoring, Operations, Red team) against the agreed draft spec. This document is the adjudicated decision record — the orchestrator's picks, not an average of the four inputs. No application code was written this session.

Season opens **Friday 2026-08-21**.

> **Amendment (post-adjudication, 2026-08-01):** after this plan was adjudicated, you decided to drop phone/WhatsApp entirely in favor of **email + PIN** as the identity/notification model — the four-agent process below argued about how to de-risk WhatsApp, not whether to replace it, so this is a direct decision layered on top, not a re-litigated agent conclusion. All affected sections below have been updated accordingly; WhatsApp is now a deferred future enhancement, not part of the launch build at all.

---

## Decisions made (gaps 1–12, plus new ones found)

1. **Three-week timeline** — phased build, see Build Plan below. Treated as a hard external constraint, not negotiable scope.
2. **Cron/sync mechanism** — **GitHub Actions scheduled workflow is primary** (fixture/result delta sync, ~10–15 min cadence on match days), with a **lightweight Supabase pg_cron health-check as a secondary watchdog** (checks "was a successful sync recorded recently," alerts admin if not — does not run the sync itself). Reasoning: a solo hobbyist under a 3-week deadline needs a primary mechanism they can debug at 11pm with `gh run list`; pg_cron's reliability edge doesn't offset that its operator (both agents proposing it, and me) has no track record running it at this cadence for a full season. See _Rejected_.
3. **Notifications: email, not WhatsApp** _(superseded post-adjudication, then partially re-superseded again — see decision 21)_. Login moves to **email + PIN** initially: same fast dropdown-name + PIN login UX as before (no change for players, no email-checking friction on a shared device). This removes the entire Meta/Twilio business-verification track from the plan (previously the single largest external-dependency risk) and lets both the pre-lock reminder and the post-result push be fully automated from week 1 via a free transactional email provider (e.g. Resend, ~3,000 free emails/month, no business verification gate). WhatsApp is not being attempted for launch at all — it's a clean future add-on, not a fallback path to maintain. **Update (2026-08-01, Auth & Player Accounts grilling session): email later demoted from required/unique identity key to optional/non-unique — see decision 21. `display_name` is the actual identity key.**
4. **Fixture seeding** — all 380 fixtures seeded once from published data. The API is only ever queried for kickoff-time changes and results, never to discover fixtures. This is the single biggest risk-reducer in the whole plan — universal agreement across all four agents.
5. **What players tip** — scorelines (confirmed, matches old app). Schema and scoring engine are built around a `pred_home_score`/`pred_away_score` pair per pick, not just result or margin.
6. **Lock and visibility** — picks lock 5 minutes before _scheduled_ kickoff (recomputed whenever a kickoff-time change is detected via sync), enforced server-side against DB time, never client clock or a disabled button. Other players' picks for a match are hidden until that match locks.
7. **Postponement after lock** — **void, no reroll, no substitute.** Three agents (data model, ops, red team) converged on this independently without seeing each other's work — the strongest signal of any decision in this document. No points either side; least disputable option, avoids "which replacement match" arguments entirely.
8. **Timezone** — UTC storage and all deadline/lock comparisons; Sydney (`Australia/Sydney`) for display only. No exceptions.
9. **Old World Cup data** — full `pg_dump` (or CSV export) of the current Supabase project, done **before** any schema changes, day 1 of week 1. A git tag preserves code, not data — both are needed. _(Not performed this session — you explicitly held off on this earlier; it's now the first item in Week 1.)_
10. **PIN auth / server-side routing** — hashed PIN (fixed 4 digits, `crypto.scrypt`), 5-attempt lockout (15 min, auto-expiring), nothing heavier (this is not a bank). Identity key is **`display_name`** (unique, case-insensitive) — see decision 21 for why this reverts the email-as-identity call in decision 3. Login itself is unchanged — pick your display name from a dropdown, enter your PIN. Because login isn't `auth.uid()`-based, Supabase RLS cannot gate rows — **all reads and writes must route through server-side Next.js API routes**, never a direct client→Supabase call. Universal agreement, zero dissent across all four agents; this is a correctness requirement, not a preference.
11. **Match-2 picker edge cases** _(timing set by you, post-adjudication)_ — state lives in DB columns on `gameweeks` (picker id, status, deadline), not app memory or cron state, so a missed cron cycle or cold start resumes safely. GW1 auto-randomizes Match 2 (no prior data exists yet); the real "last-place picks" mechanic switches on starting **gameweek 2**, using gameweek 1's score as the signal. Tiebreak order: (1) lowest score in the previous gameweek, (2) worst cumulative standing (closest to the bottom of the table — highest rank number, not lowest), (3) random among any still tied. Deadline window is "N hours after notification," capped so it can never overrun the earliest remaining kickoff. **Schedule consequence**: this needs to be built and tested by launch week, not eased in later — see Week 3 and Cut-if-behind below.
12. **Predict-the-table storage** — store the full 20-team ordering regardless of what gets scored (cheap, and any simplified scoring view derives from it, not the reverse). Exact scoring/UI shape (full ranking vs. simplified champion/top-4/relegation) is **deliberately deferred** — your call — to be decided when this feature is actually being built (Week 3), not now.
13. **Postponement before lock** _(gap found during domain modeling for issue #4)_ — a Tipped Match postponed before its picks lock is a **Skipped Slot**: the gameweek simply runs with one Tipped Match instead of two, no auto-reselected or admin-picked replacement. Distinct from decision 7 (post-lock voiding), which was already settled. See `docs/adr/0001-skip-slot-on-pre-lock-postponement.md`.
14. **Bot eligibility for season winner** _(gap found during domain modeling for issue #4)_ — **bots are eligible to win**; only the admin is excluded (decision in _New gaps found_ below, "Admin-as-player credibility risk"). No separate credibility problem for a bot winning — it doesn't control result entry. _(**Reversed 2026-08-13 by decision 43** — no bot is eligible, and the Competition Admin now is. Both halves of this entry are superseded; the reasoning above was sound on credibility grounds but missed the question that actually decided it: whether a bot winning is fun. Given the Median Bot won the retired World Cup season, it isn't.)_
15. **Bot pick-generation mechanics** _(gap from GAPS.md review, 2026-08-01)_ — three bot types carry forward, ported from the old app's actual logic (`admin_ops.py`), not reinvented: **Random Bot** (independent random plausible scoreline per side), **1-1 Bot** (always 1–1), **Median Bot** (rounded median of that match's human picks, generated only _after_ lock — a crowd reference, not a blind guess). **ELO bot is dropped**, consistent with the existing "no smart bots" decision. Your call, not a default — you explicitly chose to keep 3 of 4 old bot types rather than scoping bots out of v1 entirely.
16. **Late joiners** _(gap from GAPS.md review, 2026-08-01)_ — a player who signs up after gameweek 1 has begun. Not eligible for the season "winner" title (didn't compete the full season, same exclusion mechanism as the admin). Can submit Predict the Table at any time after joining, or skip it — both optional for them, unlike the mandatory pre-season capture for on-time players. Gameweeks before joining score 0 with no special-case logic (no picks exist for those matches).
17. **Staging Supabase project** _(gap from GAPS.md review, 2026-08-01)_ — a second free Supabase project is created alongside the production one, specifically so the week-3 dry run and general testing never touch the project that's about to go live for real players. Free tier allows 2 active projects per org; the old World Cup project (dormant since issue #3) is expected to auto-pause from inactivity around 2026-08-08, freeing headroom well before this is needed.
18. **football-data.org rate-limit sizing** _(gap from GAPS.md review, 2026-08-01, resolved by direct research rather than assumption)_ — confirmed: the Premier League is included in the free tier, at a 10-calls/minute limit. A sync cycle every 10–15 minutes doing **one batched date-range call** stays far inside that budget — no risk, provided the sync is built as one call per cycle, not one call per fixture.
19. **Session cookie / CSRF** _(gap from GAPS.md review, 2026-08-01)_ — `httpOnly` + `secure` + `sameSite=Lax` cookie, plus a custom-header check on all state-changing API routes. Sufficient for this threat model without a full CSRF-token library, since hand-rolled sessions don't get this for free the way a standard auth library would.
20. **Forgot-PIN reset** _(gap from GAPS.md review, 2026-08-01; mechanism finalized during the Auth & Player Accounts grilling session, same day)_ — admin-assisted, **forced-reset flow**: admin sets a temporary PIN (admin-typed, told to the player in person/by phone — no delivery mechanism needed) and sets a `pin_reset_required` flag. Player logs in with the temp PIN and is forced to choose a real new PIN before reaching the app; the flag then clears, along with any lockout state. Chosen over the simpler "admin just sets the real PIN directly" option — you explicitly preferred the more typical, robust pattern despite the extra `pin_reset_required` flag and login-time branch it requires.
21. **Three-environment mapping** _(gap surfaced 2026-08-01)_ — local dev (`next dev`) and Vercel Preview deployments both point at the **staging** Supabase project; only the Vercel Production deployment (from `main`) points at **production**. Free on Vercel's Hobby tier, reuses the staging project from decision 17 rather than needing a 3rd. Required discipline: apply schema migrations to staging first, confirm, then production — before merging the branch that depends on it.
22. **Identity key reverts from email to `display_name`** _(Auth & Player Accounts grilling session, 2026-08-01 — see `docs/adr/0002-email-optional-display-name-identity.md`)_ — deliberate reversal of decisions 3/10 above: not every player has their own email, and family members may need to share a parent's address, which is incompatible with email being required-and-unique. `display_name` becomes the mandatory, unique (case-insensitive) identity and login key instead; email becomes optional, nullable, and **not** unique — purely a best-effort notification-delivery field. Accepted consequence: some players won't receive the pre-lock/post-result emails.
23. **Session mechanism** — stateless signed cookie (player id + HMAC signature via a server-side secret), no DB sessions table, no expiry (persists until "Switch player"). Considered a revocable DB-backed session table; rejected because the shared-device threat model (shoulder-surfing, not remote attack, already settled elsewhere) doesn't need per-session revocation, and it would add a table plus a lookup on every request for no real benefit.
24. **Competition code storage** — env var (`COMPETITION_CODE`), checked at signup. Considered a DB-editable `settings` table (which schema v1 doesn't otherwise need — unlike the old app, nothing else turned out to require admin-editable runtime config); rejected as flexibility for a need that doesn't exist, since you're the only one who'd ever change it. **Superseded by issue #68 / `docs/adr/0004-multi-competition-foundational-scope.md` decision 1** — the code moved off the env var entirely, into a hashed (`crypto.scrypt`) `code_hash` column on the new `competitions` row, set per environment via `scripts/set-competition-code.mjs`. The original rejection of a `settings` table still holds (this isn't one); the reversal was forced by multi-competition scoping needing a `competitions` row to key off in the first place, not by the original flexibility argument turning out wrong.
25. **First-admin bootstrap** — a one-off seed script (same pattern as `scripts/seed-fixtures.mjs`) inserts the admin player row directly, rather than building the old app's "Create first admin" UI flow gated by a separate bootstrap secret. There is, and will only ever be, one admin for now. _Deferred to future work_: a competition-setup flow where the first signup auto-becomes admin, plus a user-management screen for adding players and assigning roles (player/admin) — you flagged this as a real future direction, not build-now scope.
26. **Admin capability boundary confirmed** — exactly two elevated actions (match-result/kickoff-time edits, PIN resets), zero elevated read visibility (admin is bound by the same pre-lock pick-hiding rules as any other player — no "admin sees everything early" bypass). Matches how the old app actually worked, per your description, and closes off a natural scope-creep temptation before any admin UI gets built. Admin-configurable competition-specific settings raised as a real future want; explicitly deferred, not built now.
27. **Emoji field** — added to `players` (nullable, optional at signup), shown in the login list and leaderboard. Cheap, and you confirmed it was "a fun addition to the game" in the old app worth carrying forward — easiest to add now, before any signup/login UI exists, rather than as a later migration. **Superseded by issue #127** — emoji is now mandatory at signup (route-validated allowlist against a curated library, `src/lib/auth/emoji-options.ts`, random-pick button in the join step); the column stays nullable for legacy rows, which keep the ⚽ fallback in the login list.
28. **PIN specifics** — fixed 4 digits (not a 4–6 range), hashed with Node's built-in `crypto.scrypt`. No new dependency, no native-module Vercel build risk (unlike `bcrypt`/`argon2`), and a fixed length is simpler UI for the youngest players. Lockout duration: 15 minutes, auto-expiring, failed-attempt counter resets on success.
29. **Design system timing** _(2026-08-01, superseded same day)_ — originally deferred until after backend/core feature work. **Superseded**: a separate agent now works design/frontend in parallel with backend, rather than sequenced after it. See `docs/FRONTEND_BRIEFING.md` for that agent's context. Coordination point: the backend agent (this one) owns `src/lib/**` (CODEOWNERS-gated); the frontend/design agent owns `src/app/**` and any new `src/components/`-style directories. API/data-shape contracts between them will need active coordination since the backend surface is still being built, not stable yet.
30. **Engineering process / repo standard for solo agentic coding** _(2026-08-01, 4-agent fan-out/cross-examine/synthesize process — Velocity, Correctness, Next.js/Vercel-tooling, Red-team, adjudicated by a separate synthesis agent)_ — set up specifically to balance two competing goals: agentic coding stays efficient (no disproportionate process for a true solo build), and hallucination control stays strong (Andy can't personally review Next.js/React code, so guardrails must be largely automated/objective). The process surfaced a real, live example of the risk it exists to address: CLAUDE.md and this document had drifted to disagree with each other on the scoring formula (see the scoring-divergence entry above — corrected same day).
    - **CI**: one GitHub Actions job (`test` + the `src/lib/**` golden-value guard) — not a duplicate typecheck/lint/build job, since Vercel's own build already covers those for free on every push/PR (confirmed via `next.config.ts`).
    - **Merge model**: every change goes through a branch + PR, but non-critical changes (everything outside `src/lib/**` and `.github/workflows/**`) auto-merge the instant CI passes — no human latency for ordinary work. `src/lib/**` (the five consequence-critical modules — scoring, lock enforcement, Match-2 picker, postponement, PIN/lockout) and `.github/workflows/**` are CODEOWNERS-gated, requiring Andy's explicit approval, scoped narrowly so it doesn't tax everyday UI/config/docs changes. This reconciles the two goals rather than trading one for the other — the option none of the four agents proposed individually until cross-examination surfaced that GitHub's "require PR" setting is branch-wide but CODEOWNERS review is path-scoped.
    - **Golden-value discipline**: for `src/lib/**`, a test with literal expected-value assertions (not just "a test exists") must be committed before its implementation, checked mechanically via git history ordering. See `docs/standards/TESTING_STANDARD.md` §1a for the full mechanism and why existence-only test gates are gameable.
    - **Permission separation**: the agent's day-to-day git/gh credentials must never be able to modify branch protection, CODEOWNERS, or force-push `main` — that stays Andy-only, permanently, not just at setup. This was the red-team agent's core finding: an agent that can configure a protection rule can just as easily remove it later, in a tool call indistinguishable from routine work.
    - **Rejected**: a bespoke CI grep-check against `node_modules/next/dist/docs` for Next.js version-drift risk in a diff (proposed by the Correctness agent) — the Next.js/Vercel-tooling agent's counter-argument won: a reliable version of this check is a real static-analysis project, disproportionate to three weeks and one developer. Cheaper equivalent adopted instead: the existing AGENTS.md version-drift warning is re-surfaced as a checklist item in the PR template, so it fires again at the merge decision point, not just at task start.
    - **Rejected**: a separate `docs/standards/CODING_STANDARD.md` for general TypeScript/Next.js conventions — premature while the codebase is three files. Grow `AGENTS.md` directly once real patterns exist (route handlers, forms, data-fetching), consistent with Vercel's own published finding that passive AGENTS.md-embedded context outperforms retrieval-gated skill docs.
    - **Adopted alongside**: `typedRoutes: true` (compile-time catch for a hallucinated `href`), Prettier + Husky/lint-staged pre-commit/pre-push hooks (fast local feedback, zero GitHub round-trip), `.editorconfig` explicitly skipped (moot — no human contributors with varied IDE settings).
    - **Setup complete (2026-08-01)**: fine-grained PAT (`Administration: No access`) created and swapped into the agent's day-to-day `gh auth`, replacing the prior admin-scoped classic token — verified by actually attempting a branch-protection read/write, not just checking a permissions flag (both correctly rejected with 403 `Resource not accessible by personal access token`; normal `Contents`/`Pull requests` operations confirmed still working). Repo auto-merge enabled. A ruleset on `main` is active, requiring a PR, review from Code Owners, status checks `verify` and `Vercel`, and up-to-date branches, with no bypass list. Vercel Preview Deployments confirmed already working via a real test PR (#41, merged) — its `Vercel` check posted and passed with no extra configuration needed.

**New gaps found (folded into decisions above or here):**

- **Scoring formula divergence** _(found by data-model agent, confirmed by me reading `src/tipperoos/core/scoring.py` directly)_: CLAUDE.md documented additive stacking scoring (3+2+1+1+5); the actual shipped code was tiered and mutually exclusive (Exact=5 / Goal-diff=4 / Result=3 / Wrong=0, plus +1 knockout advancement which doesn't apply to a league). **Resolved: additive**, per your call — result (3) + goal difference (2) + correct Team A score (1) + correct Team B score (1) + exact-score bonus (2), all stacking, max 9 per match. No knockout-advancement term, since there are no knockouts in a league season. _(Numbers corrected 2026-08-01 to match CLAUDE.md's current, authoritative text — a prior version of this entry stated +5/max 12, which had drifted out of sync with CLAUDE.md.)_ **Superseded 2026-08-13 by decision 43** — the formula is now additive to a maximum of **7**, with no exact-scoreline bonus and no points for a correct team score on a wrong result. Kept here because the divergence itself is the reason decision 30's process guardrails exist.
- **No health/alerting layer** _(ops agent)_: resolved via the pg_cron watchdog in decision 2.
- **Admin-as-player credibility risk** _(red-team agent)_: admin is also a competing player, which is a real dispute risk on any close scoring correction. Resolved: every match-result edit gets a timestamped `updated_by`/`updated_at` audit trail visible on the Match Centre, and the admin is explicitly flagged as **ineligible for the season "winner" title** even though they can still play for fun. _(Superseded — `CLAUDE.md`'s two-tier admin model makes a Competition Admin **eligible** for their own competition's title, because match-result correction was removed from the role entirely and their remaining capabilities can't influence scoring. Note this is the opposite of the bot rule set in decision 43: bots are ineligible, Competition Admins are not.)_
- **Match-2 deferral bootstrapping gap** _(data-model agent, found in cross-examination)_: if the real picker mechanic is deferred to gameweek 4, it needs "who finished last" history that only exists if it was being recorded since gameweek 1. Resolved: a lightweight per-gameweek standings snapshot is recorded from GW1 onward regardless of whether the picker UI itself is live.
- **football-data.org freshness SLA is undocumented for live matches** _(ship-it agent)_: mitigated by scope, not engineering — the app never needs live in-match data, only pre-match kickoff-time changes and final full-time results, which is a much smaller exposure window. Verify actual latency empirically in week 2 before trusting it for anything lock-adjacent.

31. **Display name format rules** _(2026-08-01, made while implementing the Auth & Player Accounts logic layer — not previously specified anywhere)_ — CLAUDE.md/the grilling session established `display_name` as the unique identity key but never pinned down length/character rules. Set while writing `src/lib/auth/signup-validation.ts`: 2–20 characters after trimming, letters (unicode-aware)/numbers/spaces/apostrophes/hyphens only. Emoji is excluded here since it already has its own dedicated onboarding field. Low cost to revisit — it's a pure validation function with its own golden-value test table, not a schema constraint (the `display_name` column itself is unconstrained `text`).
    - **Tooling fix alongside**: `eslint.config.mjs`'s custom `globalIgnores` had silently dropped `node_modules` from the default ignore list (only re-added `.next`/`out`/`build`/`next-env.d.ts`) and used unanchored patterns, so `npm run lint` was recursing into any nested worktree's `.next`/`node_modules`. Fixed by anchoring with `**/` and re-adding `node_modules`.

32. **Golden-value guard's test-first check stays a same-commit-tie pass, not strict-precedence** _(2026-08-01, found by an independent subagent review of PR #47, then attempted and reverted)_ — the guard (`scripts/ci/critical-module-guard.mjs`) only fails a _strict_ violation (implementation's first commit before the test's). A real attempt to tighten it to reject same-commit ties hit a structural wall: a brand-new `src/lib/**` file's test can't be committed before the file it imports exists, because `tsc` won't resolve the import, and the local pre-commit hook requires every commit to typecheck and pass tests — ruling out a red-then-green two-commit sequence without workarounds (untyped dynamic imports, disabling typecheck mid-PR, a separate stub-scaffolding PR merged ahead of time) disproportionate to a solo three-week build. **Decision: leave the guard as-is.** The mechanical check's real job is narrower than "prove test-first happened" — it's "catch the case where someone visibly reorders commits to sneak an untested implementation past review." The actual backstop for golden-value correctness is, and was always documented as, human: Andy spot-checking the golden-value table against `CLAUDE.md`'s prose at CODEOWNERS review time (`TESTING_STANDARD.md` §1a).

33. **Auth API routes + CSRF header name** _(2026-08-01, first API routes built on top of the Auth & Player Accounts logic layer)_ — `POST /api/auth/signup`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/players` (the login-selector list; excludes bots, since nobody logs in as one). CLAUDE.md's Trust section calls for "a custom header" on state-changing routes but never named one — settled on `x-tipperoos-client`, checked by `src/app/_lib/csrf.ts`. Route glue (`src/app/_lib/session-cookie.ts`, `src/app/_lib/csrf.ts`) deliberately lives under `src/app/_lib/`, not `src/lib/`, since the golden-value guard applies uniformly to everything under `src/lib/**` and there's no meaningful golden value to assert for a thin `next/headers` cookie wrapper — the logic it wraps (`src/lib/auth/session.ts`) already has its own golden-value tests. Verified end-to-end against the staging Supabase project via `next dev` + curl (signup, case-insensitive duplicate rejection, CSRF rejection, login, 5-attempt lockout, lock blocking even a correct PIN, players list, logout) before opening the PR, since no frontend exists yet to exercise it through a browser.

34. **First real screens: `/signup` and `/login`** _(2026-08-02, prototyped on `docs/DESIGN_SYSTEM.md` once the frontend agent landed it)_ — wires the auth API routes into actual pages. Shared primitives (`src/components/ui/Button.tsx`, `Card.tsx`, `TextField.tsx`, `PinInput.tsx`) built now rather than inline, since both screens needed them simultaneously — consistent with `docs/DESIGN_SYSTEM.md`'s "promote the moment a second screen needs it" rule. `PinInput` is 4 individual auto-advancing digit boxes rather than a single text field (kid-friendly, matches the numeric-keypad mobile UX). Small API addition alongside: `POST /api/auth/login`'s 401 response now includes `attemptsRemaining`, needed for `docs/DESIGN_SYSTEM.md`'s example copy ("4 more tries before a short break"). **Caveat**: this session's tooling has no browser/screenshot capability — verified via `next dev` + curl (both pages render server-side HTML with expected content, no 500s; a full signup→login round trip through the real endpoints the pages call, including the new `attemptsRemaining` field) but the actual visual rendering (spacing, the PinInput boxes, emoji picker layout) has **not** been eyeballed in a real browser. Andy should open the Preview URL and click through before treating this as visually done, not just functionally done.

35. **Login and signup merge into one competition-code-gated flow** _(2026-08-02, Andy: "when a player goes to login they should have to input the competition code first")_ — `/signup` becomes a redirect (`next.config.ts` `redirects()`) into `/login?intent=join`; `/login` is now a single `code -> list -> pin/join -> success` flow. Three decisions made explicitly with Andy before building, since each changes the implementation meaningfully:
    - **The player-name list is now actually protected**, not just cosmetically hidden: `GET /api/auth/players` requires `x-competition-code` and 403s without it. A client-side-only gate would've been bypassable via devtools in seconds, defeating the point.
    - **A device that has already entered a correct code isn't asked again** — the code is stashed in `localStorage` and silently replayed against the players endpoint on future visits; a 403 on replay (e.g. the code was rotated) clears the stored value and falls back to asking. Explicitly scoped to _this one competition_ — storing it as a single value, not an array/set, since real multi-competition support would need a `competition_id` threaded through the schema, not just a differently-shaped `localStorage` key. Noted as a known limitation for that future work, not solved speculatively now. _(Amended 2026-08-04, see decision 38/`docs/adr/0004-multi-competition-foundational-scope.md`: this originally said `competition_id` would need to reach `matches` too — that was wrong. `matches`/`teams`/`seasons` are real Premier League facts shared by every competition and must never be scoped; only `players` and `gameweeks` need it. Getting this backwards would've been worse than not scoping at all — it multiplies bug/attack surface across every fixture-sync write and result-entry action for zero confidentiality benefit.)_
    - **Signing up now counts as logged in**: the join step reuses the code already verified in step one (no second code field), and its success state is framed as already-in, not "now go log in" — matching that `POST /api/auth/signup` was already setting the session cookie on success (#49), the gap was purely in the frontend framing.
    - **Explicitly deferred**: a returning player with an already-valid session cookie who navigates back to `/login` still goes through the full flow rather than being short-circuited to "you're already logged in as X." Natural follow-up, but broader than what was actually asked for here.

36. **PR review automation — local pre-push hook, not GitHub Actions** _(2026-08-02, raised in response to "how do I set up automated review," redesigned twice before landing)_ — the engineering-process decision (30, above) deliberately leaves everything outside `src/lib/**`/`.github/workflows/**` unreviewed by anyone, human or agent, before it auto-merges on green CI. That's a real gap, not an oversight: `verify`/`Vercel` prove code is technically valid, not correct.
    - **Draft 1, post-merge GitHub Actions job**: rejected before shipping — `main` deploys straight to Vercel production, so a post-merge-only review doesn't prevent bad code from being live, it only shortens the cleanup window after the fact.
    - **Draft 2, pre-merge GitHub Actions required check**: 3 sequential lanes (correctness, security, spec-conformance) as a blocking status check, fixing in-place with a single end-of-job push and a bot-identity loop guard to stop it re-reviewing its own fix. Correct in shape, but needs `secrets.ANTHROPIC_API_KEY` — a separate billed Anthropic API key, which you don't have (Claude Code itself runs on your subscription, not a metered key). A GitHub Actions run authenticating via `claude setup-token`'s long-lived OAuth token instead of a raw API key would sidestep this and keep the stronger, un-bypassable server-side guarantee — noted here as a real option if the local version below ever proves too weak, not pursued now since you asked for local specifically.
    - **Decision: a local Husky `pre-push` hook** (`scripts/review/local-pr-review.mjs`), reusing the same 3 lane prompts (`.github/claude/review/{correctness,security,spec-conformance}.md`) against the diff vs. `main`. Uses whichever `claude` CLI session is already logged into your subscription on the machine doing the push — no API key, no GitHub secrets, and critically, no `.github/workflows/**` file at all, so none of decision 30's CODEOWNERS/agent-permission restrictions apply; this shipped through the normal auto-merge flow like any other change.
    - **Trade-off accepted, deliberately**: this is weaker than the GitHub Actions design — bypassable with `git push --no-verify`, and only protects pushes made from a machine that has the hook installed (via `npm ci`'s `prepare` script). For a solo-builder-via-agents workflow where hooks are already the enforcement mechanism for typecheck/lint/test/build, and agents are instructed never to skip hooks unprompted, this was judged an acceptable trade for "no separate API key, ships today."
    - **Mechanically different from the Actions draft**: a pre-push hook can't include a same-run fix in the push it's currently gating (git has already resolved the SHA to push before invoking the hook), so a lane that commits a fix still aborts the current push and asks for a plain `git push` again, rather than the Actions draft's single end-of-job push.
    - **Not cached across pushes**: iterating with several small pushes to the same branch re-reviews the accumulated diff each time. Accepted for now; revisit if it gets annoying at this project's scale.
    - The local hook needs no setup beyond `npm ci` (which installs the Husky hooks) and being logged into Claude Code on the machine doing the push — nothing to configure. `.github/claude/review/SETUP.md` documents the reserve GitHub Actions path instead (two secrets, the workflow file, the ruleset change), not the adopted one.
    - **Verify pass added same day** _(you asked directly: "is there a debate or synthesis step at all?")_ — there wasn't. A lane's block file or fix commit was trusted unconditionally; nothing cross-checked it before it blocked a push or landed a commit. Confirmed as a real gap, not a hypothetical one, during the PR #50+#51 retrospective review the same day: running the same lane twice against the same diff produced different answers (a "plausible" finding appearing on one run and not the other). **Added**: `.github/claude/review/verify.md`, a read-only independent check that only runs when a lane actually flags something (so the common "nothing found" case pays nothing extra) — it re-reads the code itself rather than trusting the flagging lane's reasoning, and ends with a literal `VERDICT: CONFIRMED`/`VERDICT: REJECTED` line. The verify pass never touches git itself; `local-pr-review.mjs` parses its verdict and does the actual `git reset --hard`/block-file-deletion, deliberately keeping "an LLM decides" and "code executes a destructive git operation" as separate steps. On a malformed/missing verdict, defaults to whichever outcome is safer to assume: reject an unverified fix (don't trust it), keep an unverified block (don't silently wave it through) — not a full debate/adjudication process (that's what the original 4-agent BUILD_PLAN.md process was for major decisions; disproportionate for a per-push gate), just enough independent verification that a finding has to survive a second, skeptical read before it can actually block or change anything.
    - **Verify pass skipped for docs-only diffs** _(same day, your call — "I don't 'care' really about it when it is purely docs changes")_ — if every changed file in the diff is a `*.md` doc, a lane's block/fix is trusted directly, the same as before the verify pass existed. Lanes still run against docs-only diffs (they've caught a real issue this way already — a stale cross-reference in this very document), only the extra independent-verification step is skipped, since nothing a docs-only push can do actually breaks the app.
