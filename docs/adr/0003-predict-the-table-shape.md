# Predict the Table: band-sort capture UI, band-distance scoring, standalone from Season Total

Issue #25 deferred the Predict the Table capture/scoring shape until build time, flagging that a full 20-item mobile drag-reorder is meaningfully harder to build than the alternative. Three divergent capture concepts were prototyped in a grilling session (tap-efficient default-and-bucket editor, delight-focused card-swipe draft, zero-drag sequential single-pick draft) and synthesized: players freely sort all 20 teams into 7 fixed Table Bands (Champion, Champions League, Europe, Mid Table, Lower Table, Relegation Battle, Relegated) via a single-card swipe/tap gesture against static Band targets. Sorting is free-form — a Band may be temporarily over- or under-filled — with any mismatched Band flagged and corrected via a tap-team → move-to-Band action before submission. No drag-and-drop reordering exists anywhere in this feature.

Because scoring only ever depends on Band placement, not fine position, the order within a Band is incidental (whatever order the player assigned it in) rather than a genuine ranking signal — "full 20-team ordering" is captured in name (per the storage principle already established), but only the Band-membership portion carries predictive meaning today.

Scoring is additive per team: `(7 − band_distance) − 1` (range 0–6, `band_distance` = number of Bands between predicted and actual — self-limiting to a 0 floor since the max possible distance is 6, no explicit clamp needed), plus a +10 Band Bonus per Band for exactly matching its full membership, except the Champion Band, which is worth +20 (a single-team Band, and deliberately the highest-value single pick). Maximum score: 200. Ground truth comes from football-data.org's `/v4/competitions/{id}/standings` endpoint. The score is recomputed continuously through the season against live standings, and is kept standalone from Season Total / Season Winner — an easily-reversible choice, since the full order is always captured regardless of how it's scored.

## Considered and rejected

- **Full 1–20 drag-and-drop reorder** — highest engineering risk on mobile (touch-drag physics, scroll conflicts, accessibility); explicitly what issue #25 flagged as worth avoiding.
- **Pure sequential "who's 1st, who's 2nd..." single-pick draft** — safest to build and fully robust to interruption (each pick persists immediately), but tedious: 20 forced discrete decisions with no way to move quickly past teams the player has no opinion on.
- **Pre-filled smart default** (seed with last season's table, edit only what you disagree with) — fastest path to a valid submission for a disengaged player, but dropped in favor of the more ceremonial, engaging card-sort experience.

## Update (issue #26 build): "call" framing and remove-and-recall correction

Built during issue #26 as a "calling" ritual rather than a neutral sorting task — one club dealt at a time, called into a Band, with that club's actual previous-season finishing position shown as context (or "Promoted" if it wasn't in the league last season) so a less-expert player has something to go on besides a guess. This is a presentation-layer refinement of the shape above, not a reversal of it: still 20 teams into 7 fixed Bands, still no drag-and-drop, still free-form/resumable.

One real change from the original "tap-team → move-to-Band" correction flow: tapping an already-placed team now removes it outright and sends it straight back to be called again, rather than opening a secondary picker to choose its new Band. Considered and rejected: a separate move-to-Band picker (as originally written) — dropped because it's a second interaction pattern to learn, when "remove, then use the one call gesture you already know" covers the same correction with a single mental model. Two agent-built, unconstrained prototype explorations (a physical "shelf" metaphor and a three-act "verdict" ritual) informed this direction; see the design conversation on issue #26 for the fuller comparison.

## Update (issue #26 build): team cards show real club colors

After comparing the shipped plain-pill team display against the "shelf" prototype's denser, club-colored card rows directly, the product owner chose the latter: each team is now a card with a two-tone kit-stripe rail (the club's real primary/secondary colors) plus code and full name, arranged in a grid rather than a wrapped cloud of small pills, with a Band's position range (e.g. "2–5") shown as its own badge next to the Band name. This is a deliberate, scoped exception to `docs/DESIGN_SYSTEM.md`'s "no other colors" rule — real club colors, but still no crests (the trademark constraint is unchanged and unrelated). See `docs/DESIGN_SYSTEM.md`'s palette section for the pointer back to this entry.

Fixed alongside: the original single-slot Champion display only ever rendered the _first_ team assigned there, silently hiding any extra teams if Champion ended up over-subscribed mid-correction — a real bug caught via screenshot, not a design choice. The single-slot treatment now only applies when Champion holds exactly one team; an over-subscribed Champion falls back to the same card grid every other Band uses, so every team stays visible and removable.

## Update (issue #26 build): persistent board + responsive picker, replacing the calling/reconcile phase-swap

The "call one team, then a separate review screen once all 20 are done" split (from the first `#26 build` update above) is gone. All 7 Bands are now always visible as one board — the product owner specifically liked the "Verdicts" prototype's per-Band fill-dot readout ("you can see how filled a group is") enough to want it always on screen, not just once calling finished. Choosing/moving a team's Band is now a separate **Picker**, responsive by device size rather than one fixed layout: a bottom drawer on phone-sized screens (matching the mobile-first default this app already commits to), a persistent side panel next to the board on tablet/desktop-sized screens, where there's room to show the board and the picker at once. The picker auto-advances through uncalled clubs (same "one at a time" ritual as before) or opens for a specific already-placed team when its card is tapped, to move or swap it — tapping a team's `×` still does the quick remove-and-requeue from the previous update; tapping the card body itself opens the picker instead, to reconsider without losing the team's place in the round.

**Swap** is new: if the chosen Band is already at its target size, the picker shows its current occupants instead of silently overfilling, and picking one exchanges Bands with them (or, if the team being placed hadn't been called yet at all, sends the bumped occupant back to the queue, since it has no prior Band to reciprocate into). No new API surface — both cases are just the existing assign/unassign calls run in sequence from the client, verified live against staging by replaying that exact sequence directly.

Considered and rejected: keeping the fixed-position band-picker-list-as-part-of-a-single-card layout from the previous update on larger screens too — dropped because a wider viewport has room to show the board and the decision together, and forcing the same narrow single-column flow there wastes the space without adding anything.

## Update (issue #26 build): mobile UX review fixes

A detailed UX/UI review against a mobile screenshot found two real bugs and two ambiguities, all fixed in the same pass:

- The picker drawer's heading ("Move this team") was clipped at the top edge — the drag-handle and heading rows sat too close to the drawer's rounded top corner, so the corner's own curve visually cut into the first glyph. Fixed by giving both rows more vertical clearance before any text renders.
- A club's kit-stripe was invisible whenever its secondary color was white (Leeds, Spurs, Fulham, Newcastle), since it blended into the team card's own white background. Fixed with a thin hairline seam between the two color halves plus a faint outer ring around the whole stripe — applied only when the two colors actually differ, so genuinely solid-color clubs (Chelsea, Everton, etc.) keep a clean uninterrupted bar rather than gaining a fake seam.
- `FillDots`' filled dots used to take the Band's own tone color, so a fully-filled Relegation Battle Band showed red dots that could misread as "wrong" rather than "done." Filled dots are now always a neutral ink color (a universal "how full" signal); the Band's tone now only tints the _empty_ dot outlines, as a preview accent rather than a status.
- The header above the board carried too much always-on text, and its two success messages ("Submitted..." / "Every Band looks right!") had no visual differentiation despite meaning different things. Fixed by combining the "N called" and "Locks in..." lines into one compact status row, and merging the two success messages into a single line when both are true.

Also added, lower priority per the same review: a scroll-fade hint at the bottom of the picker's band list (there was no affordance suggesting more Bands existed below the fold), and a native tooltip (`title`) on truncated team names in dense grid rows.

## Update (issue #26 build): drawer viewport-height bug, and bulk "Clear" actions

Live testing found the picker drawer overflowing past the visible screen on mobile — `max-h-[55vh]`/`85vh` are computed against the browser's full layout viewport, not what's actually visible once the address bar/toolbar chrome is showing, so the sheet rendered taller than the real screen and its lower rows ran under the browser chrome. Fixed by switching both to `svh` (small-viewport-height units, which assume the chrome is showing) so the cap always matches the guaranteed-visible area.

Separately, the product owner raised a real gap: moving a team currently forces either a straight remove-and-requeue, or — if the target Band is already full — a deliberate one-for-one **swap** with a specific occupant. Sometimes a player just wants to clear out a Band (or the whole board) and freely re-call teams into it, without picking exact swap partners. Rather than build cascade/reflow logic (a team pushes the next one down, etc. — more moving parts, more surprising edge cases for a low-stakes feature), added two simple bulk-clear actions, both reusing the existing unassign API with no new server surface:

- **"Clear all"**, next to the header status row, gated behind an inline "Clear all? Yes / Cancel" confirm (the one bulk action big enough to warrant a confirm).
- **Per-Band "Clear"**, a small text button next to a Band's header, shown only once it holds at least one team — empties just that Band back to the queue, no confirm needed since the blast radius is small and immediately re-callable.

Cleared teams return to the front of the queue in their prior order, so re-calling them is just working through the queue again — consistent with the existing single-team remove-and-requeue behavior from the second `#26 build` update above.

## Update (issue #26 build): the `svh` fix wasn't enough — drawer rebuilt on CSS Grid

The `vh` → `svh` unit swap above didn't actually fix the overflow; live screenshots afterward showed the same symptom (all 7 Bands rendered with no scroll, the last rows running under the browser's chrome). The real cause was flexbox: the scrollable band-list region was a `flex-1` child of a `flex-col` container, and flex items default to `min-height: auto`, which can win out over an explicit `max-height` cap once an absolutely-positioned sibling (the scroll-fade hint) is in the mix — so the "scrollable" region was silently sizing to its full content instead of the space actually available.

Fixed by rebuilding the Picker's frame on CSS Grid instead of flex: `grid-rows-[auto_auto_auto_1fr_auto]` gives the drag-handle, header, and team-preview rows their natural height, and hands everything else to the one `1fr` track — which is the actual scrollable list. Grid's `1fr` tracks don't carry flexbox's `min-height: auto` trap, so this holds regardless of what else is in that row. Also widened the mobile cap from `55svh` to `92svh` (a near-fullscreen sheet) so most or all 7 Bands are visible without scrolling being load-bearing in the common case — scroll is now a safety net for small screens, not the primary mechanism.

## Update (issue #26 build): code review pass

A two-axis (standards / spec) code review of the whole feature found two candidate data bugs and a handful of maintainability smells, all resolved:

- Both flagged "data bugs" — Sunderland/Leeds's `previous_season_position` values, and `CLUB_COLORS` seemingly missing Burnley/West Ham/Wolves — turned out to be **false positives**: the review had no DB access and assumed the real-world Premier League roster. This app's actual `teams` table (Coventry City, Hull City, Ipswich Town in, those three out) is the _correct_, intentional roster for the 2026/27 season being modelled here, confirmed directly with the product owner. `CLUB_COLORS` already matches it exactly (20/20 short codes) — no change needed.
- Real maintainability fixes applied: the near-identical optimistic-update/rollback pattern in `assignTeam`/`unassignTeam`/`clearTeams` was extracted into one shared `saveOptimistically` helper (apply → request(s) → roll back on failure), removing three copies of the same shape. `manualPickTeamId`/`pendingSwapBand` were renamed to `reconsiderTeamId`/`swapChooserBand` with comments naming what each actually drives, since the review found the original names didn't make the Picker's two modes (reconsider an existing pick vs. call the next queued team; plain Band list vs. swap sub-view) obvious without reading the JSX.
- Deliberately **not** done: splitting `PredictTableFlow.tsx` into smaller modules (flagged as a Divergent Change smell) and writing a new test suite for the four `table-predictions` API routes (flagged as missing coverage for the most concurrency-sensitive code in the feature). Both are real, reasonable follow-ups, but bigger and riskier than a "make the flagged fixes" pass warrants — left for a dedicated follow-up rather than folded in here.
