# App navigation shell: single extensible bottom tab bar, top-corner Switch Player

Issue #61 flagged that only two routes exist post-login (`login`, `predict-table`) with no shell connecting them — a player who lands on Predict the Table has no way back except browser-back, and every future destination (Leaderboard #24, Match Centre, Picks entry) would land as another orphaned route unless a shell exists before or alongside them. `docs/FRONTEND_BRIEFING.md` had already pre-emptively guarded against a fixed bottom nav bar's safe-area insets and named "Switch player" as a required persistent affordance, without ever deciding the shell's actual shape. Resolved via a grilling session, then stress-tested with a three-agent adversarial fan-out (UX/product, engineering/build, spec-compliance) plus a targeted codebase investigation.

## Decision

- **Destination set (v1)**: Predict the Table is the only real tab, since it's the only destination that exists today. The shell ships now rather than waiting for Leaderboard/Match Centre/Picks entry to land, and is built to accept more tabs as they become real — not designed around a speculative future tab set.
- **Shape**: a fixed bottom tab bar (icon + label, safe-area-inset padded), used at **all breakpoints**, including tablet/desktop — no swap to a top nav bar or sidebar at `md:`/`lg:`. This is a small private group, mostly on phones; one nav pattern everywhere avoids maintaining two versions that can drift, and avoids reopening the "no sidebar" decision in a slimmed-down form. Revisit only if it proves genuinely annoying on desktop in practice — not preemptively engineered around.
- **Switch Player placement**: a separate top-corner affordance (avatar/icon), not a tab-bar slot. It's an action (log out to the player list), not a navigable destination, and folding it into the tab bar would eat a scarce mobile-width slot and muddy the tab bar's semantics as more real tabs land.
- **Coverage**: the shell wraps every authenticated page, with no exceptions — including Predict the Table's locked/skipped/late-joiner states, which currently render as full-bleed centered cards with zero chrome. Login is the only excluded route (pre-auth, nothing to navigate to yet). Chrome-free authenticated pages are exactly the orphaned-route failure mode this issue exists to fix; carving out exceptions would reintroduce it on a subset of states.
  - **Exception within the exception**: Predict the Table's team-picker (a bottom drawer on phone, per `docs/adr/0003-predict-the-table-shape.md`) overlays on top of — visually covers — the tab bar while open, reappearing when the drawer closes. It's a modal, focused interaction with no navigation happening mid-picker, so hiding the tab bar underneath it isn't a wayfinding problem.
- **Landing tab**: no placeholder "Home" tab. Predict the Table is the sole tab until a second destination is real. Inventing a Home screen with nothing on it yet would be exactly the kind of speculative scope the destination-set decision above is trying to avoid.

## Structural consequences, resolved here rather than deferred

Two findings from the adversarial review turned out to be cheap to settle now and expensive to leave open, so they're pinned down as part of this decision rather than left to the follow-up implementation issue:

- **Space reservation is the shell's job, not each page's.** Every state of Predict the Table (`src/app/predict-table/PredictTableFlow.tsx`) currently uses an identical `<main className="flex min-h-full flex-1 items-center justify-center ...">` pattern, inlined per-branch, with no shared per-route layout file — only the bare root `layout.tsx` exists. A fixed bottom tab bar would clip or overlap this content if left unaddressed. Rather than retrofitting `min-h-dvh`-style fixes into every page (including future ones), the shell reserves the space once, at the root `layout.tsx` level (padding/safe-area equal to tab-bar height around `{children}`) — no edits needed to `PredictTableFlow.tsx` or any future page, since each page's content is already sized relative to its own container, not the viewport directly.
- **Switch Player is always a full route navigation, never an in-place auth swap.** The logout route (`src/app/api/auth/logout/route.ts`) already exists — it clears the session cookie via `clearSessionCookie()` but is currently unwired to any UI and does no navigation. Predict the Table's picker state (`reconsiderTeamId`, `swapChooserBand`, `assignments`, etc.) is initialized once from server props with nothing watching for auth changes, so an in-place player switch would leak the previous player's in-progress picker state to whoever logs in next on the same device — a real shared-device trust gap, not just a UI nit. Requiring Switch Player to always perform a hard navigation to `/login` means the entire route tree unmounts and this state is destroyed for free, with no explicit reset plumbing needed.

Both are contained to this implementation: the space-reservation fix is a root `layout.tsx` change only, and Switch Player is new wiring of an already-existing, currently-unused route — neither touches `src/lib/**` or any other in-flight feature.

## Considered and rejected

- **Holding the shell until Leaderboard/Match Centre exist**, so the destination set is real rather than speculative — rejected because it leaves the orphaned-route problem (the actual reported pain) live for weeks, and the shell was designed to extend cheaply anyway.
- **A header-only shell now, swapped for a bottom tab bar once 2+ destinations exist** — rejected because introducing a different nav pattern mid-season is the "reproduce the old app's clunkiness via indecision" failure mode `FRONTEND_BRIEFING.md` is trying to avoid; better to validate the real pattern (icon set, active state, safe-area handling) against a real device now.
- **A slim wayfinding-only sidebar on tablet/desktop**, distinct from the old app's dense content sidebar — considered per the issue's own prompt to re-examine that reasoning, but rejected for now: new surface area to design/maintain for a screen size this player base rarely uses, for a benefit that's speculative until the tab set actually grows.
- **Switch Player as a tab-bar slot** — rejected; it's an action, not a destination, and would give the tab bar an oddly heterogeneous mix of screens and a logout button.
- **A placeholder "Home" tab** — rejected as speculative scope; Predict the Table is the only real destination, so it's also the only tab.
- **Fixing the tab-bar/content collision per-page** (e.g. `min-h-[calc(dvh-48px)]` on every route) — rejected in favor of a single shell-level fix, since it's structurally identical for every current and future page and doesn't need re-solving per route.

## Deferred, not settled here

- **Single-tab tap behavior** (does tapping the only/active tab scroll to top, no-op, or reset?) — no existing pattern to anchor this decision, and it's cheap to change before a second tab exists. Left as an implementation note for the follow-up issue: pin down a consistent rule before tab 2 ships, so behavior doesn't silently diverge between tabs added at different times.
- **Admin's result/kickoff-correction UI's home within the shell** — not yet built, not blocking this ADR; noted so the next person building it isn't left to guess intent.
- **Z-index allocation across overlay surfaces** (picker drawer today, future modals for Match Centre edits/confirmations) — no scheme exists yet; needs one before a second overlay-using feature ships, to avoid DOM-order-dependent layering bugs.
- **Kid-friendly copy audit** for the tab label, Switch Player's label/tooltip, and locked-state messaging — a checklist item for implementation, not a shape decision.
- **Late-joiner "skip Predict the Table" landing state** — flagged in review as a potential nav dead-end (no second tab, no Home tab to land on), but accepted as a non-issue: by the time late joiners are a realistic scenario, Leaderboard/Match Centre/Picks entry are expected to already exist, giving them somewhere real to land.
- **Switch Player discoverability for the youngest players** (~10 years old) — a top-corner icon is a deliberate bet against maximal discoverability in exchange for keeping the tab bar purely navigational; accepted as a reasonable tradeoff, not re-litigated.
